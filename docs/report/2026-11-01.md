- `v1.2.0` [v1.2.0](<https://github.com/sogeisetsu/opencode-skill-management/releases/tag/v1.2.0>) — `sogeisetsu/opencode-skill-management`
  > # v1.2.0
  > 
  > \`skill\_management\` gives every installed OpenCode skill a switch: list what is installed, find out
  > why one will not load, hide it from the model, and put it back. Disabling writes \*\*one\*\* global
  > \`skill\` permission rule — no skill file is ever moved, edited or deleted.
  > 
  > \*\*No breaking changes in 1.2.0.\*\* The four actions, their inputs, the JSON envelope, the written
  > rule shape, the same-line marker and the single-file layout are unchanged since 1.1.0.
  > 
  > ## Fixed since v1.1.0
  > 
  > - \*\*\`list\` no longer reports "N skills differ across other agents" on every call.\*\*
  > \`summary.diverged\` counted hidden internal agents (\`title\`, \`summary\`, …), which carry
  > \`{\*,\*,deny}\`; on a real machine that made every skill look divergent (33/33) and added a noise
  > warning to each \`list\`. Only \*\*visible\*\* agents are compared now; \`inspect.agents\[\]\` still lists
  > every agent, so the detail is not lost.
  > - \*\*Frontmatter booleans no longer contradict each other.\*\* \`disable-model-invocation: "false"\` is a
  > string, and \`Boolean("false") === true\`, so \`inspect\` reported it as \`true\` while \`list\` reported
  > \`autoinvoke: false\` for the same file. \`true/yes/on/1\` and \`false/no/off/0\` (quoted or not) are
  > normalized now, and both fields go through the same rule.
  > - \*\*A failed sidecar write no longer turns a successful config change into an error.\*\* Once the
  > config was written and verified, a sidecar write failure used to surface as \`internal\_error\`: the
  > file really changed, but the result had no \`changed\` / \`diff\`. It now returns \`ok: true\`,
  > \`changed: true\`, keeps \`diff\`, sets \`sidecar: null\`, and explains itself in \`warnings\`. The config
  > change is not rolled back.
  > - \*\*\`enable\` is no longer blocked by an unrelated file's syntax error.\*\* It reads sidecar-recorded
  > config files alongside the target; before, any of them failing to parse plus "no candidate rule"
  > produced \`config\_unparsable\`. The hard refusal now applies only to the \*\*target\*\* config file;
  > other files are reported in \`warnings\` by name.
  > 
  > ## Also since v1.1.0
  > 
  > - \*\*The installer checks before writing.\*\* If \`opencode.json(c)\` already lists this package in
  > \`plugins\`, or a second copy sits in \`plugins/\`, it refuses and exits with code \`2\`, leaving every
  > file untouched — two sources make the host report \`Duplicate plugin ID\` and fail one of them.
  > - New installer flags: \`--check\` / \`--dry-run\`, \`--uninstall\` (deletes only this plugin's file),
  > \`--npm\` (asserts the npm channel, never writes), \`--force\`, \`--json\`. \`&lt;config&gt;\` resolves the way
  > the host resolves it (\`$OPENCODE\_CONFIG\_DIR\` first).
  > - The plugin exports \`PLUGIN\_VERSION\`, asserted against \`package.json\` by the harness.
  > - The acceptance harness grew from 260 to \*\*326 assertions\*\*, and now validates every action's
  > \`output\` against the declared JSON Schema (required fields, property types, \`error.code\` /
  > \`error.message\`) and asserts that \`content\` is the same data as \`output\`.
  > - README is down to 51 lines; field tables, installer flags, package contents, usage and the test
  > workflow moved to the documentation site.
  > - The documentation site gained \*\*Design decisions\*\* (why permission rules instead of policies, why
  > there is no \`allow\`, why global-only, why text edits plus a same-line marker, why the sidecar is
  > only an audit trail — each with its cost) and \*\*Development & verification\*\* (harness sections,
  > CI, the performance and release gates, npm package contents, why two copies cannot coexist).
  > The \*\*Permissions\*\* page now expands Effects into a \`deny\` vs \`ask\` comparison with three real
  > skill examples. English and Chinese stay mirrored.
  > 
  > ## What it does
  > 
  > | Action | What you get | Writes config |
  > |---|---|---|
  > | \`list\` | Every registered skill and its effective state for the \*\*calling agent\*\* (\`available\` / \`disabled\` / \`ask\`) | No |
  > | \`inspect\` | Why one skill is (not) usable: the matched rule, per-agent differences, how the id was derived | No |
  > | \`disable\` | Hidden from the model-visible list and rejected at load (\`effect: "ask"\` keeps it listed with confirmation) | Yes |
  > | \`enable\` | Deletes the one blocking rule, whoever wrote it | Yes |
  > 
  > Permissions are evaluated for the \*\*calling agent only\*\*: last match wins (\`findLast\`, with \`\*\`
  > and \`?\` globs), and \*\*no match falls back to \`ask\`, not \`allow\`\*\*.
  > 
  > The rule \`disable\` writes is exactly this line (the trailing comment is the provenance marker
  > \`enable\` uses):
  > 
  > \`\`\`jsonc
  > { "action": "skill", "resource": "windows-shell", "effect": "deny" } // skill\_management
  > \`\`\`
  > 
  > Writes are atomic, preserve indentation, key order, line endings (CRLF/LF) and BOM, keep one
  > backup, and are verified by reloading the host and polling the caller's rule set; a write the host
  > did not pick up is rolled back.
  >
