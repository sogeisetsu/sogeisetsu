  > ## What this is
  > 
  > \`skill\_management\` adds a switchboard for the skills installed in your OpenCode setup: see what is installed, find out why one will not load, take one out of the model's view, and put it back.
  > 
  > Disabling never touches skill files. It writes \*\*one\*\* \`skill\` permission rule into your global config (\`effect: "deny"\`, or \`"ask"\` for a soft disable). Nothing is deleted, moved or rewritten, and removing that rule restores the skill exactly as it was.
  > 
  > This is the first stable release: the surface described below is frozen for 1.x.
  > 
  > ## What it does
  > 
  > | Action | What it does | Writes config |
  > |---|---|---|
  > | \`list\` | Every registered skill with its effective state for the calling agent (\`available\` / \`disabled\` / \`ask\`) | no |
  > | \`inspect\` | Why one skill is (un)available: the matching rule, per-agent differences, how its id was derived | no |
  > | \`disable\` | Hide it from the model and reject loading it (\`effect: "ask"\` keeps it listed and asks on load) | yes |
  > | \`enable\` | Remove the blocking rule again, whoever wrote it | yes |
  > 
  > How a permission is resolved: the host reads the rule set of \*\*the agent that is calling\*\*, takes the last match (\`findLast\`) with \`\*\` / \`?\` globs, and — when nothing matches — falls back to \`ask\`, not \`allow\`. That is why \`list\` and \`inspect\` evaluate per agent and name the agent they used.
